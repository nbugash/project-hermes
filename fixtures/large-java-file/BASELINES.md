# Measured baselines

**Measured**: 2026-09-05 · Linux x86_64 · Java 25 · tree-sitter 0.26.13 core, Java grammar 0.23.5,
natives built `-O3 -DNDEBUG` · 30 warm-up iterations, 200 samples, single-character insert.

## Two fixtures, deliberately

| | `Large.java` (synthetic) | `RealCorpus.java` (real) |
|---|---|---|
| Lines | 50,021 | 50,038 |
| Bytes | 1,458,404 | 1,822,885 |
| Shape | 1,270 class declarations nested inside **one** outer class | 451 **sibling** top-level types |
| Origin | generated by a Gradle task | assembled from Gradle-cache sources jars |

## Results

| Measurement | Synthetic | Real | Budget | Verdict |
|---|---|---|---|---|
| Full parse | 242.1 ms | 170.5 ms | 500 ms (SC-005a) | PASS |
| Reparse p50 | 4.383 ms | 1.963–2.271 ms | — | |
| **Reparse p95** | **5.753 ms** | **3.249 ms** (worst of 3 positions) | **5 ms (SC-004)** | **PASS on real Java** |

Real-corpus reparse by edit position:

| Position | p50 | p95 | splice | parse | bytes re-read |
|---|---|---|---|---|---|
| start | 2.271 ms | 2.812 ms | 0.550 ms | 1.237 ms | 94,208 |
| middle | 2.024 ms | 3.249 ms | 0.403 ms | 1.402 ms | 98,304 |
| end | 2.146 ms | 2.320 ms | 0.562 ms | 1.046 ms | 92,095 |

## What the two fixtures show

**Structure dominates, not size.** The real corpus is 25% *larger* in bytes and re-reads roughly
70× more source per edit, yet reparses in *half* the time. The synthetic fixture's cost came from
nesting 1,270 types inside a single outer class: every edit forces tree-sitter to rebuild a spine
through one enormous child list, work that real Java — shallow, with many sibling top-level types —
never asks for.

This is why the earlier synthetic-only measurement read as an SC-004 failure at 6.2 ms p95. The
budget was never the problem; the fixture was.

## Caveats, stated so they are not rediscovered

- `RealCorpus.java` is assembled from many real files with `package` and `import` lines stripped. It
  **parses but does not compile** — names collide and imports are gone. That is sufficient for a
  parsing measurement and misleading for anything else.
- The assembled corpus happens to contain **no non-ASCII**, so it does not exercise the UTF-8/UTF-16
  translation. That path is covered by unit tests (`Utf8Utf16OffsetsTest`, `NonAsciiOffsetTest`)
  rather than by this measurement. Five of the 1,101 source files scanned did contain non-ASCII, so
  a real editing session will hit it.
- All figures are Linux x86_64. macOS and Windows remain unmeasured (T098).
- `build-real-corpus.sh` reproduces the corpus only where the same Gradle cache contents exist. It is
  a measurement aid, not a checked-in fixture.


## JMH: the full per-keystroke path (added 2026-09-05, T051)

`IncrementalReparseBenchmark`, SampleTime mode, 3x2s warm-up, 5x2s measurement, 1 fork, real corpus:

| Benchmark | p50 | p95 | p99 | p99.9 |
|---|---|---|---|---|
| `insertOneCharacter` (rebuild mirror + reparse) | 3.400 ms | **5.501 ms** | 5.941 ms | 25.361 ms |
| `insertOneCharacter`, second run | 2.572 ms | **4.162 ms** | — | — |
| `rebuildMirrorTextOnly` (no parsing at all) | 0.506 ms | 0.560 ms | 0.584 ms | 1.539 ms |

**Run-to-run variance is significant: p95 came out at 5.501 ms and 4.162 ms on two runs of the same
benchmark.** The full keystroke path therefore *straddles* the 5 ms budget rather than clearly
missing it, and any single run should not be quoted as a verdict. What is stable across runs is the
gap against `RealCorpusBudgetTest`'s 3.249 ms reparse-only figure, and its cause. That test builds the edited string outside its timed region; the benchmark builds
it inside, which is what the product does — `didChange` calls `Document.apply` before it reparses.

Two effects account for the gap:

1. **The mirror rebuild itself**, 0.56 ms p95, measured directly above.
2. **Allocation pressure.** Every keystroke allocates and copies the whole document twice — once as
   a new `String` in `Document.apply`, once as a new `byte[]` in the adapter's splice. At 1.8 MB
   each that is ~3.6 MB of garbage per character typed, and the p99.9 of 25 ms is the collector
   arriving. Research recorded the same shape of outlier and attributed it to allocator churn.

The second effect is the one that matters architecturally: it is O(file size) work per keystroke,
which is exactly what Principle VI exists to eliminate, hiding in the mirror rather than in the
parser. See T107.


## Keystroke to committed frame (T052, Playwright, real backend + real corpus)

Measured in-page via requestAnimationFrame + MessageChannel, never from the driver's clock.

| Caret position | p50 | p95 | Dropped frames |
|---|---|---|---|
| Line 1 | 14.10 ms | 26.90 ms | 0 |
| Last line (50,038) | 14.90 ms | 23.70 ms | 0 |

**Provisional, and worse than the product should now be.** They were taken from a bundle built
before Monaco's web worker was correctly wired: the `?worker` import failed to resolve, the build
errored, and a shell chain that discarded build output kept re-running the previous `dist`. Monaco
therefore ran tokenization on the main thread — the same thread servicing keystrokes — for every one
of these runs. They are kept as the pre-fix reading; see the row below for the corrected figures.

**These numbers do not decide SC-001a.** They were taken under `xvfb` with no GPU — Chromium logs
`Exiting GPU process due to errors during initialization` and falls back to software compositing,
which inflates every frame. The budget assertion is therefore gated behind `VEGA_PERF_GATE=1`, to be
run on GPU-accelerated hardware; the dropped-frame assertion runs everywhere, because software
rendering makes frames slower without making the editor skip them.

**Zero dropped frames at both ends of a 50,000-line file** is the meaningful result available here:
typing at line 50,038 is no worse than at line 1, which is the property the incremental design
exists to produce.


## Full-document tokenization (T063, JMH, real corpus)

| Measurement | p50 | p95 | Budget |
|---|---|---|---|
| Walk the whole tree and encode every token | 137.4 ms | 182.5 ms | 800 ms (SC-005b) | 

**PASS, with roughly threefold headroom.** This is the background fill issued after the first
viewport paint, so it is allowed to be slower than the keystroke path — but it shares the worker
pool, and a fill that overran would arrive late for the whole session rather than once.

Both the tree walk and the encoding are inside the measurement. Timing only the walk would miss that
the encoder scans the document text to turn offsets into line/column pairs.


## Scroll smoothness (T061, Playwright + gpuBenchmarking, real backend + real corpus)

Driven through `chrome.gpuBenchmarking.smoothScrollBy`, which puts input into the real scroll
pipeline. `requestAnimationFrame` deltas run on the main thread and cannot see compositor work,
which is where scroll jank lives (research D7).

| Gesture | Frames | Frames over 32 ms |
|---|---|---|
| Wheel, 10 legs of 2000 px | 1,577 | **0** |
| Keyboard, 60 x PageDown | 70 | **0** |
| Ctrl+End across 50,038 lines | 90 | 1 |

The single long frame on the jump to the end is the one-off cost of relocating the viewport across
the whole document; sustained scrolling produces none at all. Note this is software compositing under
xvfb, so the frame *budget* is gated behind `VEGA_PERF_GATE=1` — but dropped frames are meaningful
here regardless, because software rendering makes frames slower without making the compositor skip
them.

**Never-visited regions render styled text** (T062): after jumping to the end of a document whose
initial request covered only the opening viewport, lines still render with multiple token spans. The
background full-document request (T064) is what makes that true.


## Corrected anchors (2026-09-05) — and an error-state result

Every real-corpus keystroke measurement above anchored on `lastIndexOf("return ")`. In this corpus
that lands inside a **javadoc comment** (`* @return The partition ...`). Edits inside a comment are
structurally insignificant and reparse differently from edits in code, so those measurements were
anchored in the wrong place. Found while building the error-state benchmark: a guard asserting the
fixture had actually entered an error state kept failing, because garbage inserted into a comment is
still valid Java.

All three measurement sites now anchor on an indented `return` statement, which is real code, and
the benchmarks carry a `codeAnchor` helper explaining why.

| Benchmark (code anchor) | p50 | p95 | Budget |
|---|---|---|---|
| `insertOneCharacter` — mirror rebuild + reparse | 2.654 ms | **4.202 ms** | 5 ms (SC-004) |
| `insertOneCharacterWhileBroken` — same, unmatched `}` present | 2.707 ms | **4.334 ms** | 5 ms (SC-004) |
| `rebuildMirrorTextOnly` | 0.501 ms | 0.530 ms | — |
| `tokenizeWholeDocument` | 137.4 ms | 194.8 ms | 800 ms (SC-005b) |
| `RealCorpusBudgetTest` reparse, worst of 3 positions | 1.8–2.4 ms | **2.947 ms** | 5 ms (SC-004) |

**The correction did not change the verdict.** Reparse on a code anchor is marginally *cheaper*
(2.947 ms vs 3.249 ms p95), so the comment anchor was not flattering the result — it was simply
measuring something other than what the criterion describes.

**SC-006 costs nothing measurable.** Reparsing with a long-lived unmatched brace in the document is
within noise of reparsing valid code (4.334 vs 4.202 ms p95). Error recovery does not degrade the
budget, which is the property T072 existed to check and the one most likely to have been false.

**On the earlier "over budget" reading:** the full keystroke path has now measured 5.501, 4.162 and
4.202 ms p95 across runs. Most runs sit inside the budget. The double whole-document copy (T107) is
still real and still worth removing — it is 0.5 ms of pure copying plus the allocation pressure
behind the 25 ms p99.9 — but it should not be described as putting the path over budget.


## After T107 — copies removed from the keystroke path (2026-09-06)

`PieceText` replaced `Document`'s substring-and-concat rebuild; `SourceBuffer` replaced the adapter's
per-edit byte array. Same corpus, same machine, benchmarks changed to measure `Document.apply`
rather than a `substring + concat` stand-in.

| Benchmark | Before | After |
|---|---|---|
| `insertOneCharacter` p50 | 2.654 ms | **1.677 ms** |
| `insertOneCharacter` p95 | 4.202 ms | **2.208 ms** |
| `insertOneCharacter` p99.9 | 25.361 ms | **3.746 ms** |
| `insertOneCharacterWhileBroken` p95 | 4.334 ms | **2.159 ms** |
| mirror update p95 | 0.524 ms | **0.001 ms** |
| `tokenizeWholeDocument` p95 | 194.8 ms | 174.8 ms |

**SC-004 now has 56% headroom** (2.2 ms against 5 ms), and the p99.9 tail fell by seven-eighths.

The tail is the more important number. It was garbage collection, and ADR-0003 deferred this work
partly because the estimate counted only the direct copying cost — 0.5 ms — and not the allocation
pressure that produced the tail. Measuring the benefit rather than reasoning about it would have
shown that in the p99.9 column of a benchmark that had already been run. ADR-0004 records the
reversal.
